## Context

See proposal.md — Why. What the code actually does today, verified:

- **One policy per table does everything.** `migration-v16-workspaces-unify.sql` loops over `crm_companies`, `crm_contacts`, `crm_deals`, `crm_activities` and `crm_tasks` creating `for all using (crm_is_member(workspace_id)) with check (...)`. `crm_is_member` is a security-definer function returning true for a direct member or an admin of the parent agency. It does not know the caller's role.
- **All CRM data writes go through the user's own client.** Every contact, deal and activity write in `app/crm-actions.ts` uses `c.supabase`, the request-scoped client carrying the user's JWT, so RLS genuinely applies to them. The service-role client appears only for workspaces, members, invites, API keys, and the automation engine.
- **There is no delete anywhere in the product.** No server action and no screen deletes a contact, company, deal, activity or task. The only `.delete()` calls on workspace data are `automations` in `app/automations-actions.ts:82`, and membership and invite rows through the service-role client.
- **API keys bypass RLS entirely.** `lib/crm-api.ts` authenticates the key and then works through `createAdminClient()`. Permissions come from the stored scope list, which contains read and write scopes and no delete scope.
- **`crm_invites.role` is stuck at two values.** v14 created it with `check (role in ('admin','member'))`; v16 widened only `crm_members` to include `agency_admin`. The two constraints have been out of step since.
- **The invite-claim path already carries any role.** `getWorkspace` inserts `crm_members` with `inv.role` verbatim, so a new role needs no new code there once the constraints allow it.

## Goals / Non-Goals

**Goals:**
- The database, not the interface, is what refuses a write. A hidden button is a courtesy; the policy is the control.
- One place decides a caller's effective role, so the four policies per table cannot disagree with each other or with the application.
- Nothing that works today stops working, apart from the two capabilities the proposal names as deliberate removals.

**Non-Goals (design level):**
- No role hierarchy machinery. Four roles resolved by one function, compared with `in (...)` lists. A permission table joined at query time would be slower and harder to read for a set this small.
- No attempt to make API keys role-aware. They are a separate authorisation system by construction; conflating them would mean re-routing every API handler off the service-role client, which is its own change.

## Decisions

### 1. One `crm_role(ws)` helper, four policies per table

```sql
create or replace function public.crm_role(ws uuid)
returns text language sql security definer stable as $$
  select coalesce(
    (select m.role from public.crm_members m
      where m.workspace_id = ws and m.user_id = auth.uid()),
    (select 'agency_admin' from public.crm_workspaces w
      join public.crm_members m on m.workspace_id = w.parent_workspace_id
      where w.id = ws and m.user_id = auth.uid()
        and m.role in ('admin','agency_admin') limit 1)
  );
$$;
```

Then, per table, generated by the same `do $$ ... foreach` loop style v16 already uses:

```
for select  using (crm_role(workspace_id) is not null)
for insert  with check (crm_role(workspace_id) in ('admin','agency_admin','member'))
for update  using (...) with check (...)      same three roles
for delete  using (crm_role(workspace_id) in ('admin','agency_admin'))
```

`security definer` is required for the same reason v16 needed it: a policy on `crm_contacts` that queried `crm_members` directly would re-enter RLS and recurse.

`crm_is_member` is redefined as `crm_role(ws) is not null` rather than deleted, because other policies written in v16 and v18 reference it and this change should not have to find all of them to stay correct.

*Rejected — keep `for all` and add a role check inside it.* A single policy cannot distinguish the verb, so delete could not be separated from update. That is the entire point.

*Rejected — enforce in the server actions only.* The anon key is public by design, so an action-level check is a suggestion to well-behaved clients. The threat this change addresses is precisely a request that does not go through the application.

*Rejected — a `viewer` that also cannot read some columns.* Column-level grants exist (v18 uses them on `profiles`) but they multiply the surface and the proposal scopes reading as unrestricted.

### 2. Application guards for the message, not for the enforcement

Server actions gain an early `if (c.ws.role === 'viewer') return { error: 'readonly' }`, and the two admin-only actions a matching admin check. These exist so a refused action produces a Hebrew sentence naming the required role. Without them RLS returns a row count of zero or a policy violation, which surfaces as either a silent no-op or a raw Postgres string — both worse than an explanation.

This is deliberately redundant with the policy, and the redundancy is the design: if a guard is ever forgotten on a new action, the policy still refuses the write.

### 3. A viewer sees a read-only screen, not a disabled one

Write controls are omitted from the markup for a viewer rather than rendered `disabled`. A disabled control still occupies the layout and invites a click; the screen reads as broken instead of as read-only. One Hebrew line states the account has read-only access, so the absence is explained rather than mysterious.

The role is already resolved server-side on every CRM page through `getWorkspace`, so this is a prop, not a new fetch.

### 4. `viewer` is added to both check constraints, and `agency_admin` to the invites one

```sql
crm_members: check (role in ('admin','member','agency_admin','viewer'))
crm_invites: check (role in ('admin','member','agency_admin','viewer'))
```

Fixing the invites constraint is in scope because this change is the one that touches it, and leaving a known-broken `agency_admin` invite in place while adding a fourth role beside it would be knowingly shipping the same bug twice.

### 5. A viewer cannot log activity either

The alternative — a viewer who may add notes but change nothing else — is defensible: a read-only teammate who cannot leave a comment is close to useless. It is rejected for now because an activity write also moves `last_activity_at` and rescores the contact, so "just a note" silently reorders the contact list. If Eran wants commenting teammates, the right shape is a fourth role or a separate note permission, not a hole in this one.

### 6. Automations and autonomy move to admin-only for writes

`automations` gets the same four-policy treatment, with delete restricted to admin. `autonomy_settings` currently has one `for all` member policy; its write verbs become admin-only while read stays open to every role. Autonomy decides whether an AI agent acts without being asked, which is not a setting a read-only or junior member should be able to flip.

`automation_runs` is left alone. It is an append-only log written by the engine through the service-role client, and restricting it would gain nothing.

## Risks / Trade-offs

- **A policy mistake locks the owner out of his own CRM.** → This is the real risk of the change. The migration is applied and verified against the spec's admin-retains-access scenario before the app is deployed, and rollback is a single re-run of the v16 policy loop, which is preserved verbatim as a commented block at the foot of the new migration.
- **Redefining `crm_is_member` affects policies this change did not write.** → The redefinition is semantically identical to the original (`true` for a direct member or an inheriting agency admin), so every existing reference keeps the behaviour it had. Verification includes listing `pg_policies` before and after and diffing the set.
- **A member loses automation deletion and autonomy control with no warning.** → Named as breaking in the proposal. Eran is the only admin today and the CRM has no other members yet, so the practical blast radius is zero at the moment of change.
- **`for insert` policies have no `using` clause, only `with check`.** → A common way to write these wrongly. Each verb's policy is written out explicitly rather than generated from a shared template, and the verification step queries `pg_policies` to confirm the intended set exists per table.
- **A viewer can still read everything, including deal values.** → Scoped out on purpose: this change is about writing. A person who should not see revenue should not be in the workspace.
- **RLS does not cover the automation engine, which runs as service_role.** → Correct and intended: automations are workspace-level behaviour, not a user acting. Worth stating so it is not later mistaken for a hole.
- **No audit trail, so an admin deleting data is still invisible.** → Named as a non-goal. This change reduces who can destroy data from every member to admins only; it does not record the act.

## Migration Plan

1. Record the current policy set: `select tablename, policyname, cmd from pg_policies where schemaname='public' order by 1,2`. Keep the output for the diff.
2. Apply `migration-v20-role-enforcement.sql` in the Supabase SQL editor — helper function, widened constraints, per-verb policies on the seven tables. Idempotent, in the v14-to-v18 style.
3. Verify as the admin that reading, creating, updating and deleting all still work, before any app change is deployed. If they do not, run the rollback block at the foot of the migration.
4. Deploy the app with the role guards and the read-only UI.
5. Invite a viewer to a scratch workspace and walk the spec's refusal scenarios, including the direct-request ones, which are the only proof that enforcement is at the database and not in the interface.

**Rollback:** re-run the commented v16 policy block at the foot of the migration to restore the blanket `for all` policies, then revert the app deploy. The role check constraints can keep the extra values; a constraint that permits a role nobody holds is inert. No data is migrated, so there is nothing to restore.

## Open Questions

None. The one open design question — whether a viewer may log activity — is resolved in decision 5 rather than deferred, because it changes a spec requirement and therefore cannot be left open.
